# Known limitations

- No authentication or private account isolation. Container builds label this a shared demo; use synthetic purchases. DigitalOcean credentials now authenticate and the app proposal validates, but no public deployment success is claimed yet. SQLite on App Platform is ephemeral; source deployment is one instance per app service.
- Live CPSC supported normalizer is intentionally limited to official notice 26-792. Its exact affected-product description is checked; unfamiliar restrictions require manual review. Other recalls are discovered but cannot become verified positives without a tested normalizer. Catalog coverage is not comprehensive.
- Bright Data search succeeded through the actual MCP server, but scrape_as_markdown returned “Customer is not active.” User is handling activation; further Bright Data requests stopped. No live manufacturer extraction claimed.
- Gemini PNG/PDF extraction and an OpenAI bounded decision request succeeded. This account cannot use legacy gemini-2.5-flash-lite; ignored local configuration selects gemini-3.5-flash-lite. Provider schema is structural; Pydantic still enforces dates, string lengths and forbidden extra fields locally. Generation caps and duplicate-import reuse reduce cost. Credit totals are not independently verified.
- Scanned identifiers require explicit in-app user confirmation before exact matching. Once a purchase has opportunities or an active run, identifier edits are blocked; import a corrected record instead. This does not verify subjective settlement declarations.
- Live settlement discovery covers one manually source-reviewed case and exact Kroger merchant records only. Other Kroger affiliates and all other cases are unsupported. Administrator/court-linked PDFs must match reviewed hashes; revisions fail closed pending renewed rule review. All personal class/proof/exclusion conditions remain uncertain; information packets are preparation-only, even after local approval. No medical details, signature or payment amount is collected. Five-row replay keeps its separate fictional settlement.
- Sentry local errors, traces, logs, masked replay and readable application frames are proven in docs/sentry-setup.md. No production deployment or production source-map upload is claimed; a build-time upload credential and deployed verification remain necessary.
- No HyperFrames output, Tiger Data connection, Snowflake Cortex query, scheduler or Devpost submission. P2 deferred; no externally posted artifacts.
- SQLite and in-process BackgroundTasks suit a local demo. Runs are bounded to 90 seconds; backend restarts mark unfinished runs partial. Product processing is sequential for deterministic database/event order; external providers are bounded and cached. No distributed or durable worker guarantee.
- Source policy checks exact HTTPS hosts, public DNS addresses and redirects for supported manufacturer URLs. URLs are not supplied by users. This is not a general-purpose arbitrary-web researcher.
- Ready-for-review describes the draft, not complete evidence or formal eligibility. Required model/serial photos and disposal confirmation remain missing until user supplies them independently. No declarations or external submissions exist.
- Browser verification used port 3001 because unrelated career-ops occupied 3000. Clean-clone Make defaults remain 3000; both apps were started with `make dev WEB_PORT=3001`.
- Browser acceptance recording is an automated walkthrough, not a narrated 90-second judge video. The exact 90-second live presentation script is in DEMO.md.
- One upstream Starlette TestClient deprecation warning remains visible in test output. It is not a failing check.

- Failed settlement-source refresh now invalidates previous approval/export and labels historical sources unavailable. A later successful refresh creates a new unapproved draft; old approval never silently returns.
